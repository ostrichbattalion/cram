## What is cram?

`cram` is a command-line study tracker built around the SAQA notional hours framework. The name is intentionally ironic — it exists specifically so you don't have to cram. By grounding your study plan in credits, notional hours, and a five-phase learning model, it replaces guesswork with a principled daily recommendation.

It tracks five modules across a full semester, knows where you are in each module's learning arc, recommends what to study today, and logs your sessions with topic-level granularity and confidence tracking.

It requires no internet connection, no account, no subscription. It is a folder of Python files and a JSON file.

## The Ideas Behind It

### SAQA Notional Hours

Every module in the South African qualifications framework carries a credit value. Ten notional hours equate to one credit. Notional hours represent the agreed estimate of total learning time for an average learner to meet the defined outcomes — including contact time, assignments, self-study, and assessment preparation.

`cram` uses this as its foundation. You never manually set a study target. Instead, the target is derived:

```
notional_hours      = credits × 10
contact_hours       = 3  (fixed for distance learning)
assignment_hours    = total_questions × 2  (SAQA-aligned estimate)
self_study_budget   = notional_hours − contact_hours − assignment_hours
```

This gives every module a principled, defensible study budget rather than an arbitrary number.

### Five Study Phases

A semester has a natural structure that most trackers ignore. `cram` models it explicitly across five phases:

```
Phase 1 — First Exposure     (20%)   CA topics, first pass through content
Phase 2 — Active Learning    (25%)   Deepen understanding, complete assignment
Phase 3 — CA Review          (15%)   Consolidate before the CA test
          ── CA TEST ──
Phase 4 — New Content        (20%)   Final arc topics, first pass
Phase 5 — Final Review       (20%)   All topics, second pass before exam
          ── FINAL EXAM ──
```

The semester arc is symmetric: roughly equal content on each side of the CA. This means the phases mirror each other in cognitive demand, with CA and final reviews being lighter because the content is already partially familiar.

Each module tracks its current phase. The burn-down, recommendations, and topic display all adapt to where you are in the arc.

### Topic-Level Confidence Tracking

Chapters (called topics in `cram`) are not binary. You do not simply "do" a topic and move on. Understanding builds through multiple exposures across weeks. `cram` tracks this with four confidence levels:

| Level | Meaning |
|-------|---------|
| 1 | First exposure done — shaky |
| 2 | Working understanding — can follow examples |
| 3 | Solid — could explain it |
| 4 | Mastered — exam confident |

Crucially, `cram` records *how many hours it took* to move between confidence levels. Over a semester you build a personal profile: this module takes me about 4 hours to move from 1→2, this one takes 6. That data makes future semester planning more accurate.

### Interleaving Across Modules

The daily recommendation engine does not tell you to finish one module before starting another. Research consistently shows that interleaving topics — studying multiple subjects across days rather than grinding one to completion — produces better long-term retention.

`cram` enforces a soft interleaving rule: no more than two modules per day, one primary focus and one shorter revisit. It tracks neglect at both the module and topic level, flagging anything that has gone untouched for four or more days, and factors this into its urgency scoring alongside deadline proximity and confidence levels.

### Weekly Study Pool

Rather than a rigid daily target, `cram` works with a weekly pool of hours that redistributes dynamically:

- Default weekday budget: 2 hours
- Default weekend budget: 3 hours
- Weekly pool: 16 hours

If you mark a day as off or light, the remaining pool redistributes across active days. If you have an intensive session and bank surplus hours, subsequent days lighten automatically. The pool never pushes a single day beyond 4 hours regardless of accumulated surplus.

Four day states are supported:

| State | Hours | Effect |
|-------|-------|--------|
| `off` | 0 | No recommendations, pool redistributes |
| `light` | ~1 | Capped, slight redistribution |
| `active` | ~2–3 | Normal (default) |
| `intensive` | logged | Surplus banked, upcoming days lighten |

## The Modular Architecture

`cram` is deliberately split into independent layers. Each file has one responsibility and no knowledge of the others except through clean interfaces.

```
cram/
├── cram.py          Entry point. Parses CLI args, wires everything together.
├── models.py        Pure data classes. No I/O, no display.
├── database.py      JSON persistence. Load, save, find, archive.
├── scheduler.py     WeeklyPlanner + DailyRecommender. No display.
├── display.py       All terminal rendering. No mutations.
├── commands.py      CLI command handlers. Calls database + scheduler.
└── data/
    ├── modules.json   Module, topic, and session data.
    └── planner.json   Weekly day-state and hours log (auto-generated).
```

### Dependency Flow

```
cram.py
  ├── commands.py  ──►  models.py
  │                ──►  database.py
  │                ──►  scheduler.py
  ├── display.py   ──►  models.py
  │                ──►  scheduler.py
  └── database.py  ──►  models.py
```

Nothing in `models.py` knows about display or persistence. Nothing in `display.py` mutates state. `scheduler.py` reads models but never saves anything. This separation means any layer can be replaced without touching the others — the path to a TUI or web interface runs entirely through `display.py`.

### The Data Hierarchy

```
Module
├── code, name, nqf_level, credits
├── current_phase (1–5)
├── ca_written (bool)
├── topics: [ Topic, ... ]
│     ├── number, name, arc (ca|final)
│     ├── sessions: [ Session(date, hours, note), ... ]
│     └── confidence_history: [ ConfidenceEvent(level, date, hours_at_change), ... ]
├── assignment: Assignment(total_q, completed_q, due_date)
├── ca:    Assessment(kind=ca, due_date)
└── final: Assessment(kind=final, due_date)
```

All study budgets, burn-downs, and neglect signals are derived from this structure at runtime. Nothing is hardcoded — add a session and every calculation updates automatically.

## Quick Start Guide

### Requirements

Python 3.10 or higher. No external dependencies.

### Setup

```bash
# Clone or download the cram/ folder
cd cram

# Run immediately — data/modules.json is pre-populated
python cram.py
```

### Your First Session

Open the detailed view to see your modules and where you stand:

```bash
python cram.py
```

Check what cram recommends studying today:

```bash
python cram.py --plan
```

Log a study session against a specific topic (module name, topic number, hours):

```bash
python cram.py --log-session "big data" 1 1.5
python cram.py --log-session "big data" 1 1.5 --note "focused on IoT architecture"
```

Update your confidence on that topic once it has shifted (module name, topic number, confidence):

```bash
python cram.py --confidence "big data" 1 2
```

After writing a CA test, mark it done and advance the module to Phase 4:

```bash
python cram.py --ca-written "big data"
```

## Command Reference

### Views

| Command | Description |
|---------|-------------|
| `python cram.py` | Detailed view — all modules, all topics |
| `python cram.py --compact` | One-line-per-module summary |
| `python cram.py --plan` | Today's recommended study plan |
| `python cram.py --log` | Full study log, all modules |
| `python cram.py --log "stats"` | Study log filtered to one module |
| `python cram.py --archived` | Show archived modules |

### Logging Sessions

```bash
# By topic number
python cram.py --log-session "machine learning" 3 1.5

# By topic name fragment
python cram.py --log-session "stats" "probability" 2.0

# With a note
python cram.py --log-session "programming" 6 1.0 --note "queues click now"
```

`--log-session` takes: module name (partial match ok), topic number or name fragment, hours as a decimal.

### Confidence

```bash
# Set topic 3 in Machine Learning to confidence level 2
python cram.py --confidence "machine learning" 3 2
```

Confidence levels: `1` shaky → `2` working → `3` solid → `4` mastered.
The hours logged at the moment of change are recorded automatically.

### Assignment Progress

```bash
# Mark 2 more questions complete in the ML assignment
python cram.py --assign "machine learning" 2
```

### Dates

```bash
# Set CA or final exam date once released by the institution
python cram.py --set-date "programming" ca 2026-05-13
python cram.py --set-date "programming" final 2026-06-20
```

### Phase Management

```bash
# Advance to the next phase
python cram.py --phase "stats" next

# Set a specific phase directly
python cram.py --phase "stats" 3

# Mark CA as written (advances to phase 4 automatically)
python cram.py --ca-written "big data"
```

### Day State

```bash
python cram.py --day off         # rest day, no recommendations
python cram.py --day light       # short day, budget capped at 1h
python cram.py --day active      # normal day (default)
python cram.py --day intensive   # surplus hours banked
```

### Archive

```bash
# Move a completed module out of the active view
python cram.py --archive "information systems"

# View archived modules
python cram.py --archived
```

### Typical Daily Workflow

```bash
# Morning: check the plan
python cram.py --plan

# After studying: log the session
python cram.py --log-session "stats" 2 1.5 --note "worked through examples"

# If confidence shifted during the session
python cram.py --confidence "stats" 2 2

# Evening: check the overview
python cram.py --compact
```

## Future Ideas

These are directions worth exploring as the project matures.

### TUI Interface

The modular architecture was designed with this in mind. `display.py` is the only layer that needs replacing. `textual` (Python) would give a multi-panel interactive interface with keyboard navigation, persistent module selection, and modal dialogs for logging sessions — without touching `models.py`, `database.py`, or `scheduler.py`.

### Weekly Summary View

A `--week` flag showing the week's study activity across all modules: hours logged per day, subjects touched, total against pool, confidence changes made. This was deliberately deferred from the initial build to keep the main views uncluttered, but the session data already supports it fully.

### Semester Carry-Over

At the end of a semester, archive all modules cleanly and initialise a new set for Semester 2. The archived data remains queryable. Over time this builds a personal study history — you can see how your hours-to-confidence ratios change as you grow as a learner.

### Personal Calibration

Once you have a few semesters of data, the SAQA phase weights (20/25/15/20/20) could be replaced with weights derived from your actual session history. If you consistently need 30% of your time in Phase 1 for technical modules, the planner should know that.

### External Course Integration

Distance learning students often supplement with online courses (Coursera, YouTube series, etc.). These could be tracked as a parallel `ExternalCourse` type alongside modules — same session logging and confidence tracking, but without the SAQA notional hours framework, just a simple hour budget you define.

### Notifications

A small script run via cron that prints a reminder when a CA is within 3 days or a module has been neglected for 7+ days. One line in crontab, no dependencies beyond what already exists.

### `--help` Per Command

argparse provides basic help but topic references (`--log-session` accepting either a number or name fragment) are not immediately obvious. A `--help-log`, `--help-confidence` style expanded help system would lower the friction for new users.
